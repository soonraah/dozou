## 1. 診断の要約

前回の個人基盤 (my-data-platform) は約 2 年・207 commit をかけたが、取り込めたのは MoneyForward の手作業 CSV だけで、可視化には届かなかった。
時間の多くは enterprise level を目標にした土台 (Terraform の 2 環境、CI/CD) と model 設計 (Data Vault 2.0 → medallion) に流れ、開発は集中期と最長 12 か月の空白を繰り返した。
今回は AI agent で開発の手間が下がる見込みがあるが、source ごとの運用負荷 (API の変更、token の失効、手作業での取得) は下がらない。
動かせない前提は、Mac が常時起動ではないこと、運用は月 1 時間以内であること、そして開発がまた止まりうることである。

## 4. 関係者の視点

個人の基盤なので、他者の代わりに「別の立場の自分」を反対者として置いた。
各立場の見方は、私 (Claude) が出した候補から本人が「実際に言いそうなもの」を選んだものである。

| 立場 | その視点から見た問題の説明 | 裏づけ・反証となるデータ |
|---|---|---|
| 現在の自分 (著者) | 前回は開発が面倒で止まった。面倒だったのは、MoneyForward の CSV の形式合わせ、dlt の作法の調査、BigQuery への load 設定である。AI coding でこれは解消できる。enterprise level の目標と Data Vault は過剰だった。1 つの source を早く可視化まで通せば、興味は逃げにくい | 面倒だった作業はいずれも、source や tool の固有の知識を調べて合わせる作業で、AI が得意な種類である。一方で、2025 年の AI coding 期にも可視化に届かなかった (3 節) |
| 半年後の自分 (運用を担う立場) | 構築は楽しかったが、壊れた取り込みを直すのが面倒で放置している。データは溜まっているが、dashboard を開いていない | 現在、各データを見ていない (2 節)。Oura の token や Todoist の API 終了のように、source 側の変更は実際に起きている (2 節) |
| 業務の自分 (データエンジニアの立場) | 業務で毎日やっていることを休日にもやるのは、楽しみにならない | 前回は業務の作法 (IaC、2 環境、Data Vault) を個人に持ち込み、可視化に届かなかった (2 節) |
| セキュリティ担当の自分 | 認証情報がある環境で AI agent に Bash を実行させること自体が risk である | Claude Code の sandbox は Bash にしか効かず、WebFetch と MCP は別に許可が要る (01-exploration.md) |

### 意見が割れている点

- **AI で問題が解けるか。** 現在の自分は、前回止まった理由 (開発の面倒さ) は AI で解消できると見ている。半年後の自分は、止まる原因は開発ではなく運用 (壊れた取り込みの修理) と、見なくなることにあると見ている。前回の AI coding 期の実績は、どちらの見方も否定しきれない。
- **LLM と credential の risk。** 現在の自分は、LLM にデータを渡す risk は低く、守るべきは認証情報だと見ている。セキュリティ担当の自分は、認証情報がある環境で AI agent が command を実行できること自体を risk と見ている。両者は「認証情報を守る」点では一致しており、AI agent と認証情報が同じ環境にあってよいかで割れている。

## 6. この戦略が満たすべき条件

| もとのブロッカー | 満たすべき条件としての言い換え |
|---|---|
| 各 source の認証で人間の手作業が要る場合、運用コストが高くなる | source ごとに、認証の手作業が何回・何分要るかを見積もり、合計を月 1 時間の予算に収める。収まらない source は対象から外すか、取得頻度を下げる |
| 趣味のプロジェクトなので、途中で飽きる | 開発が数か月止まっても、取り込みと backup が無人で続き、再開したときに壊れていない |
| 同上 (目に見える成果がないと興味が逃げる) | 最初の集中期のうちに、少なくとも 1 つの source を取り込みから可視化まで通す。以降の集中期も、終わりに見られる可視化が残っている |
| 前回は過剰な目標と modeling で止まった | raw export を残し、軽い model を持つ。Data Vault 級の複雑な modeling はしない |
| 業務と同じことを休日にやっても楽しくない | 業務の stack をそのまま再現せず、休日の楽しみとして成立する形にする |
| (前提) | CI/CD は初期に作る。ただし前回は CI/CD があっても可視化に届かなかったので、それだけでは足りない |
| 認証情報は守りたい | 認証情報はローカルの git 外、または GitHub secrets などに置き、repo には入れない |

| 取り組み | 時期 | 結果 | そこから分かること |

### 自分自身の関与

- 「enterprise level の運用」を目標にしたこと、Data Vault 2.0 を採用したことは、本人の判断である。本人はこれを過剰だったかもしれないと認めており、今回の問題につながっていると見ている。
- local 環境の案を「スケーラビリティとメンテナンス」を理由に退けたのも本人の判断である。今回の要件 (個人の規模、運用は月 1 時間以内) のもとで、この理由が今も成立するかは確かめていない。
- 探究の結果、本人は次の点で考えを変えた。
  - 集めることと可視化することは、それ自体が目的に含まれる
  - LLM は境界になるが、渡すデータの risk は低く、守るべきは認証情報である

## 8. 探究との突き合わせ

| 参照した事例・診断 | 判定 | 理由 |
|---|---|---|
| (a) Willison: 1 file の DB は copy も backup も楽 | 調整が必要 | 確かに楽だが、copy や backup を自動化すれば 1 file かどうかの差は小さい |
| (b) Quantified Self の落とし穴: 記録するものが多すぎる / 問いがない (Choe et al. CHI 2014) | 調整が必要 | AI coding で、source を増やすときの構築コストは下がる。一方で、source ごとの運用負荷 (API の変更、token の失効、手作業での取得) は source の数に比例して残る。これは「運用は月 1 時間以内」という制約と衝突しうる |
| (c) 業務の振り返り: IaC と CI/CD を最初から整えたのが良かった | そのまま当てはまる | 1 人の基盤でも CI/CD は重要で、初期に作るほど効果が大きい。ただし前回は CI/CD があっても可視化に届かなかった |
| (d) karlicoss/HPI: raw export を残し、解釈は code で後からやる | 調整が必要 | raw export を残すのはよい。ただし毎回 code で解釈するのではなく、ある程度 model 化したものを持ちたい。Data Vault のような複雑な modeling はしない |
| (e) cloud の無料枠には条件がある | そのまま当てはまる | 無料枠の条件が変われば移行が必要になる |
| (f) Gordon Bell は lifelogging をやめた | そのまま当てはまる | 集める楽しさが続くとは限らない。前回の 12 か月の空白とも整合する |

## 11. 保留した解決策案

- GitHub Actions で取り込みを定期実行し、認証情報は GitHub secrets で管理する
- 認証情報はローカル PC 上の git 外に置くか、都度 login する
- 可視化に BI tool ではなく Claude Dashboards のような手段を使う
- 最初に 1 つの source を取り込みから可視化まで通す
- raw export を残し、その上に軽い model を置く
