## 洗練の要約

診断の中で、間違っていたら戦略全体が崩れる論点を 3 つに絞った。
1 つ目は、今の AI agent なら 1 つの source を短期間で可視化まで通せるか (A)。
2 つ目は、source ごとの運用負荷が月 1 時間に収まるか (C)。
3 つ目は、軽い model で足り、model 設計で止まらないか (E)。

これらを 6 週間の戦略テストで確かめる。
切り口は 2 つで、手作業の source (MoneyForward) と自動取得の source (Todoist) である。
手作業の source だけでは無人運用と運用負荷を試せない。
そのため、自動取得の source を 2 本目として加えた。

現時点ではテストを始める前であり、どの論点もまだ検証していない。
結果はこのドキュメントに追記する。

## 洗練の対象

### 検証する論点

| 論点 | なぜここが「てこ」なのか | 検証の結果 |
|---|---|---|
| A. 今の AI agent なら、1 つの source を短期間 (1 回の集中期のうち) で取り込みから可視化まで通せる | 前回は約 2 年かけて可視化に届かず、12 か月の空白が生じた。「早く可視化すれば興味が逃げない」「AI で開発の手間が下がる」は、どちらも本人の見立てで、まだ検証していない。2025 年の AI coding 期にも可視化に届かなかった実績がある | 未検証 |
| C. source ごとの運用負荷 (認証の更新、手作業での取得、壊れたときの修理) が、合計で月 1 時間に収まる | 運用は月 1 時間以内という制約がある。AI で下がるのは開発の手間であり、運用の手間は source の数に比例して残る。ここが外れると、対象にできる source の数が決まらない | 未検証 |
| E. raw の上に軽い model (medallion 程度) を置けば、可視化に十分で、model 設計で止まらない | 前回は Data Vault から medallion への切り替えで止まった。model 設計に時間が流れる失敗の再発を防げるかどうか | 未検証 |

### 対象にしなかったもの

- **B. Mac が常時起動でなくても、取り込みと backup が無人で続く**: 本人の選んだ上位 3 つに入らなかった。ただし 2 本目の切り口 (Todoist の日次取得) で自然に観察できるため、副次的な指標として記録する。
- **D. local の DuckDB で足りる (前回 local を退けた理由が今回は成立しない)**: 外れても数週間の手戻りで済むと本人が見積もっているため、独立した検証はしない。テストの中で問題が出たら記録する。

## 使った手法と選定理由

| 手法 | 使ったか | 理由 |
|---|---|---|
| 戦略テスト | 使う (主) | A、C、E はどれも、机上で model を作るより、小さく作って確かめる方が早い |
| システムモデリング | 簡易版を使う (補助) | C について、source ごとの運用予算の表を作り、テスト中の実測と突き合わせる。stock と flow の model を作るほどの複雑さはないため、別ファイルには切り出さず、本ドキュメント内の表で済ませる |
| Wardley マップ | 使わない | cloud の無料枠や AI agent の変化は 01-exploration と 02-diagnosis で扱った。外れても数週間の手戻りで済むため、5 年先を見通す必要は薄い |

## 戦略テストの記録

- **テストする切り口 (最も狭く、最も深い部分)**
  1. MoneyForward: 月次の手作業 CSV → raw → 軽い model → 可視化 1 枚
  2. Todoist: GitHub Actions で日次に取得 → raw → 可視化
- **スポンサー / ガイド**: 1 人の基盤なので、どちらも本人が兼ねる。開発は AI agent に任せる。スポンサーとガイドの分離がないため、「自分の当てに都合の悪い結果を軽く扱う」リスクがある。これを抑えるため、指標と終了条件を先にここへ固定しておく。
- **週次の振り返り**: 週に 1 回、15 分のセルフレビューを行う。指標を記録し、詰まった点を書く。学びのない週が 2 回続いたら、切り口を狭める。
- **期間**: 6 週間 (2026-11-23 〜 2027-01-04 を目安とする)
- **指標** (導入できたかではなく、影響を見る)
  - A: 最初の可視化までにかかった人間の作業時間。さらに、作った可視化をテスト期間中に自分から何回開いたか。集めること自体も目的に含まれるため、開く回数が少なくても直ちに失敗とはしない。まず測ってみる。
  - E: model を作り直した回数。2 本目の source を足すときに、既存の model を変えずに済んだか。
  - C: source ごとの月あたりの手作業の時間 (分)。取り込みが壊れた回数と、直すのにかかった時間。
  - B (副次): Mac を開かなかった日のあとに、取りこぼしや手作業での補修が要ったか。
- **先に決めた終了条件**
  - A、C、E が見込みどおりなら、方針策定 (step 4) に進む。
  - 6 週間たっても最初の可視化に届かない場合は、A が外れたとみなし、診断に戻る。
  - 2 本目の source の運用だけで月 1 時間を超える場合は、C が外れたとみなし、対象にする source の基準を見直す。

### テスト設計の時点で確認したこと

- 当ての中に、整合を確かめていない組み合わせがある。GitHub Actions は cloud 上で動き、DuckDB はローカルの Mac にある。Actions で取得したデータを、電源が入っていない Mac の DuckDB にどう届けるかは、まだ決まっていない。これは解決策の設計の問題なので、ここでは決めない。ただし、Todoist の切り口で必ず直面する。直面したときの摩擦を学びのログに記録する。
- 新しい基盤を作ること自体を目的にしない。目的は、A、C、E を確かめることである。
- 自分の当てにのめり込みすぎて、「うまくいっていないかもしれない」を受け入れられなくなることを避ける。そのため、終了条件を上に固定した。

### テスト用に仮置きした構成

テストを動かすために、次の構成を仮置きする (2026-11-23 決定)。
方針として確定したものではなく、step 4 で改めて決める。
テストの結果 (特に C の運用負荷) は、この構成のもとでの値として記録する。

| 要素 | 仮置き | 選んだ理由 / 差し替え |
|---|---|---|
| storage / 計算 | DuckDB + DuckLake。catalog と Parquet はどちらも Mac 上に置く (2026-11-23 更新) | ACID transaction を使いたい。S3 の認証なしで参照でき、agent も sample data で開発できる |
| Actions とローカルの受け渡し | Actions は raw file を S3 に書き、Mac は起動時にそれを読んで DuckLake に取り込む | 共有 catalog を持たずに済み、テスト対象 (A・C・E) に関係しない部分を増やさない |
| cloud storage / backup | S3 (2026-11-23 決定) | GitHub Actions の OIDC に公式対応しており、Actions に長期 key を置かずに済む。B2 は GitHub Actions の token が使えるかを確認できていない |
| 取り込み | dlt | 前回面倒だった dlt の作法を AI agent がどこまで肩代わりするかを、A の検証として確かめる |
| 変換 | dbt-duckdb | 業務で慣れている |
| model | raw + 軽い medallion | Data Vault 級の modeling はしない |
| 可視化 | DuckDB UI | 準備が最小。dashboard 向きではないが、後から差し替えられる |
| 認証情報 (Actions) | S3 は OIDC と IAM role、Todoist の token などは GitHub secrets | S3 用の長期 key を GitHub に置かない |
| 認証情報 (ローカル) | 1Password (`op`)。`op://` 参照だけを置き、必要な command だけを `op run` で包む | 平文を disk と設定から消せる (2026-11-23 更新)。[調査](https://claude.ai/artifact/V8WB9bywr1Zn37hAZRLQd3) |

決めずに後回しにするもの: LLM / MCP からの接続、暗号化、3 つ目以降の source。

DuckLake について、テストで守る前提は次のとおりである。

- ACID の範囲は DuckLake への書き込みである。Actions が S3 に raw file を置く処理は、同じ transaction に含まれない。
- backup では catalog と Parquet の整合を保つ。
- DuckLake に由来する詰まりは、学びのログで他の詰まりと区別して記録する。最初の可視化を妨げる場合は、通常の DuckDB に戻す。
- 将来は、安価または無料枠の BaaS に catalog を置き、data を S3 に置く構成への移行を目指す。これは本人の希望であり、方針としては step 4 で判断する。

ローカルの認証情報について、テストで守る前提は次のとおりである。

- `op` は平文を消す手段であり、AI agent に対する境界ではない。`op run` で注入した値は、その command から読み出せる。
- `op run -- claude` のように agent 本体を包まない。
- AI agent には `op` を実行させない (2026-11-23 決定)。desktop app 連携は本人の全 vault にアクセスでき、承認後は session 中 `op` が使える状態が続くためである。agent は認証情報なしで、手元の sample data を使って開発する。S3 との実際の同期は、本人が自分の terminal で `op run` を実行する。この手作業の時間は C の運用予算に含めて計測する。
- DuckDB の persistent secret は `~/.duckdb/stored_secrets` に暗号化されずに保存されるため使わない。dlt の `secrets.toml` と dbt の `profiles.yml` にも平文を書かない。
- S3 の権限は用途ごとに分け、最小権限にする (Actions は IAM role で raw への書き込み、Mac は raw の読み取りと backup 先への書き込み)。

#### 実装セッションの前提

戦略テストの実装は、この戦略ドキュメントを作るセッションとは別のセッションで行う。
実装を始める前に Claude Code の sandbox を有効にし、agent から `op` を使えないことを本人が確認する。
候補の設定は次のとおりである。確定した設定ではなく、実装セッションで検証して調整する。

```json
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "filesystem": {
      "denyRead": ["~/.aws", "~/.duckdb", "~/.config/op"]
    },
    "network": {
      "allowedDomains": ["github.com", "pypi.org", "files.pythonhosted.org"]
    }
  }
}
```

- `op` を `excludedCommands` に入れない。入れると sandbox の外で実行される。
- `allowUnixSockets` と `allowMachLookup` に 1Password 向けの許可を入れない。
- sandbox が制限するのは Bash とその子 process である。Read tool、Edit tool、WebFetch、MCP server、hook は対象外なので、Read tool には別途 deny rule を設定する。
- network の制限は hostname 単位である。`github.com` のような広い domain は、持ち出し経路になり得る。

DuckDB UI には閲覧回数の記録がない。A の「自分から何回開いたか」は、週次の振り返りで自己申告として記録する。

### 方針に持ち込む制約・前提

現時点では、テストの前提として次を置いている。いずれも方針として確定したものではない。

- 認証情報は状況に応じて扱う。GitHub Actions で定期実行するものは secrets に置く。ローカルでは 1Password (`op`) を使い、平文を置かない。
- storage は Mac 上の DuckLake (DuckDB) とし、backup は S3 に置く。
- raw export を残し、その上に軽い model を置く。medallion 程度までとし、Data Vault 級の modeling はしない。
- 可視化の手段は未定。Claude Dashboards は候補の 1 つにすぎない。

### 捨てたアイデア

現時点ではなし。

### 分からないままのこと

- A、C、E はすべて未検証である。
- B (無人で続くか) と D (local の DuckDB で足りるか) は、独立した検証をしていない。
- Actions とローカルの受け渡しは、テスト用に「raw file を S3 に置き、Mac が DuckLake に取り込む」形を仮置きした。
- DuckLake の catalog に DuckDB と SQLite のどちらを使うかは決まっていない。dlt と dbt-duckdb の DuckLake 対応状況も確認していない。
- BaaS に catalog を置き、Actions と Mac の両方から書き込む構成は確かめていない。使える BaaS、無料枠の範囲、費用、認証情報の扱いも未確認である。
- 可視化の手段は、テスト用に DuckDB UI を仮置きした。方針としては決まっていない。
- AI agent に `op` を実行させない手段として sandbox を候補にしたが、`op` と 1Password desktop app の通信を止められるかは未検証である。公式 docs に 1Password についての記載はなく、実装セッションで本人が確認する。
- S3 の実際の費用は未計測である。B2 にも OIDC federation はあるが、GitHub Actions の token が使えるかは確認していない。
