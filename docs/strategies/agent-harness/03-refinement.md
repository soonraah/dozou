## 洗練の要約

解決策の当ては「1 つの機能を、spec の作成から PR 作成まで人間の介入なしで通せる」状態である。
当面は人間が spec の承認だけを行い、最終的には spec の作成も agent に任せることを目指す。
この当てが成り立つかを、今ある最小構成で実際の機能を通す戦略テストで確かめる。
検証する論点は、介入なしで通せるか (L2)、部分的な DoD でも完了を判定できるか (L1)、環境依存や運用作業を増やさないか (L5) の 3 つである。
テストは 2026-11-30 頃に始め、2027-01-04 に中間見直し、上限は 2027-03-31 とする。
現時点ではテスト結果がなく、すべての論点は未検証である。

## 洗練の対象

### 検証した論点

| 論点 | なぜここが「てこ」なのか | 検証の結果 |
|---|---|---|
| L2: 人間の介入なしに spec から PR まで通せるか。止まるとすれば permission の確認、判断の依頼、品質不足のどれか | 解決策の当てそのものである。dozou では agent が止まった・失敗した記録が無く、業務の観察を当てはめているにすぎない | 未検証 |
| L1: DoD や E2E が一部にしか無くても、agent が完了を判定できるか | 診断の中心課題であり、業務でのやり直しの主因 (完了基準が伝わらない) と同じ根を持つ | 未検証 |
| L5: harness が Mac 環境への依存や人手の定期運用作業を増やさないか | 条件 3 (repo とわずかな手作業で再現できる) と条件 4 (運用は月 1 時間以内) が崩れると、戦略が運用予算を超える | 未検証 |

### 対象にしなかったもの

| 論点 | 理由 |
|---|---|

| L4: 作業を小さく区切れば文脈を失わない | 探究の事例 A が強く支持している。dozou での実データは L2 のテストで副次的に取れる |
| L6: security を後回しにしても後で締めたときに壊れない | requirement.md で security を後回しにすると決めている |

## 使った手法と選定理由

| 手法 | 使ったか | 理由 |
|---|---|---|
| 戦略テスト | 使う | dozou に失敗データが無く、agent がどこで止まるかも分からない。問題が曖昧な段階なので、実際に通して摩擦の在り処を見る |
| システムモデリング | 使わない | 突き合わせる実データが無く、効果を数値で見積もる段階ではない |
| Wardley マップ | 使わない | 5 年先まで効かせる戦略ではない。model の進化が速いという論点 (診断の視点 ④) は未解決のまま残す |

## 戦略テストの記録

- **テストした切り口 (最も狭く、最も深い部分)**: 次の 2 つを、この順に試す。
  1. (ii) data に依存しない小さな機能 (補助 script など)。原因を harness に絞り込みやすい簡単な切り口。
  2. (i) MoneyForward の CSV 1 ファイルを dlt で取り込む機能。personal-data-platform の戦略テストの最初の一歩を兼ねる、複雑な切り口。dozou 固有の完了判定 (L1) も試せる。

  各機能の結果を見て harness を改善し、次の機能で再び試すループを回す。ほかの data source や機能も対象に含めてよい。
- **最初の構成**: superpowers、pre-commit、PR template に、薄い指示書を足したもの。探究の B 案 (最小限で始め、失敗が起きた箇所から育てる) の検証を兼ねる。
- **spec の扱い**: 当面は人間が spec の承認だけを行う。最終目標は spec の作成も含めて agent に任せること。
- **スポンサー**: 本人
- **ガイド**: 本人
- **週次会議**: 日曜日に 15 分の振り返り (本人のみ)。介入の記録、やり直しの有無、増えた運用作業を見る。
- **期間**: 2026-11-30 頃に開始。2027-01-04 に中間見直し。上限は 2027-03-31。
- **指標**:
  - L2: spec を承認してから PR ができるまでに人間が介入した回数と種類 (permission の確認 / 判断の依頼 / 品質不足のやり直し)
  - L1: PR を review した時点で完了基準を満たしていたか (やり直しの回数)
  - L5: harness を新しい環境で再現するのに必要な手作業の数、テストを通して増えた人手の定期運用作業の数
- **先に決めた終了条件**:
  - 2 機能続けて介入 0 回かつやり直し 0 回なら、方針策定 (step-4-policy) に進む。
  - 3 機能続けて同じ種類の介入が起きるなら、その種類を診断に戻して切り口を変える。

## 洗練の結果

### 診断に加える更新

- 条件 2 の期限: 「〜2027-01-04」を「上限 2027-03-31、延長可」と読み替える。条件の本体は期限ではなく「戦略テストを止めない」ことにある。
- 観察の追加: superpowers の brainstorming は人間との対話を前提にしている。「spec の作成から介入なし」という当てとぶつかる可能性がある。
- 観察の追加: spec は、人間の意図と完了基準が agent に渡る唯一の場所である。spec の作成から人間が抜けると、診断の中心課題 (完了基準が伝わらない) が悪化する可能性がある。

### 方針に持ち込む制約・前提

- superpowers は使いたいが、自律的な実行の妨げになる場合は外すことがある。
- 業務の harness 構成より、walkinglabs などの教科書的な手法をベースにする。
- spec の作成は、当面は人間が承認する形で始め、最終的には agent に任せる形へ移る。

### 保留した解決策案

ステップ 4 (方針) で検討する。

- 週次の振り返りの定期化。候補と制約は次のとおり。
  - cloud の scheduled task (`/schedule`): 自動で動くが、Mac にある session の記録は読めない。cloud での無人実行は現時点で考えていない。
  - Mac の launchd などから `claude -p` を起動する: session の記録を読めるが、Mac が常時起動ではないため実行されないことがある。
  - 振り返り用の skill / slash command を作り、日曜に手動で実行する: 自動ではないが、環境に依存しない。
- 介入の記録を、session の transcript (`~/.claude/projects`) から集計する。

補足調査 ([research-skills-plugins.md](research-skills-plugins.md)) から加えた候補は次のとおり。
テスト開始前には入れず、テスト中に実際に起きた介入ややり直しへの対策として検討する。
先に入れると、L2 の観測に最小構成の挙動と plugin の効果が混ざり、B 案の検証にならないためである。

- superpowers の brainstorming が「介入なし」とぶつかった場合の代わりとして、feature-dev (Anthropic 公式) を使う。
- L1 (完了判定) への打ち手:
  - 作る agent と評価する agent を分ける (Anthropic の evaluator)。
  - JSON の feature list を使い、agent が変えてよい項目を `passes` だけに絞る。
- 切り口 (i) (MoneyForward の取り込み) の補助として、dlt の AI harness や dbt Labs の dbt-agent-skills を使う。
